### Gazebo ###

# Before launching, clean up any stale processes/shared memory from previous sessions.
# NOTE: killall matches on the 15-char truncated process name, which misses Gazebo
# Harmonic's real process names (gz sim server / gz sim gui / parameter_bridge). A
# survivor here keeps a gz-transport advertisement alive on /clock, which makes the
# NEXT gz sim fall back to a namespaced clock topic ("Found additional publishers on
# /clock") — controller_manager then waits forever ("No clock received") and
# `ros2 topic hz /clock` shows nothing. Use pkill -f (matches full cmdline) instead:
#
# There was ALSO a second, more fundamental cause of the same symptom, now fixed in
# gazebo.launch.py: camera_bridge used to bridge /clock BIDIRECTIONALLY
# (.../Clock@gz.msgs.Clock). Because gz_sim and camera_bridge start in parallel with
# no ordering, the bridge's own ROS->GZ /clock advertisement could win the race
# against gz_sim's own clock publisher, forcing gz_sim onto the namespaced
# /world/empty/clock topic instead of plain /clock — reproducible even from a
# perfectly clean launch, no stale processes required. Fixed by making the /clock
# bridge GZ->ROS only (.../Clock[gz.msgs.Clock) since nothing needs to push ROS time
# into Gazebo anyway.
pkill -9 -f "gz sim"; pkill -9 -f "parameter_bridge"; pkill -9 -f "move_group"; pkill -9 -f "rviz2"; pkill -9 -f "robot_state_publisher"
rm -rf /dev/shm/fastrtps_* /dev/shm/ros_*

# Verify clean slate before launching — should print nothing:
ps aux | grep -iE "gz sim|parameter_bridge|move_group|robot_state_publisher" | grep -v grep
